# 记忆结构改造的公开数据评测协议

状态：预定义的下一轮实验协议。本包只运行 schema/索引导入验证，不提供新结构的召回率或吞吐量对比。

## 1. 与已有结果的关系

已有公开数据检索结果是 BM25 与 TF-IDF，评测对象是固定原始证据单元。LoCoMo 采用 turn，LongMemEval 采用 session；两者粒度不同，不直接横向比较百分比。已有索引包含 LoCoMo 原文与 caption，新的 SQLite 导入演示只索引原文。因此演示的 FTS 排名不可直接当成相同设置下的升级效果。

随包的 `reports/baseline_snapshot.json` 从之前的汇总文件直接提取，保留原文件 SHA256。其数字是**先前基线**，不是本次结构化数据层的测量。

## 2. 冻结输入和标注隔离

索引进程只接收白名单字段：原始对话内容、来源自带角色/名字、session/turn 标识、原始日期、可用的图片描述等。是否使用 caption 必须在所有比较组一致，并记录字段投影。

禁止把 `qa` 内 question/answer/evidence、`answer_session_ids`、`has_answer`、`question_type` 或人工 gold 的衍生标签输入索引、事件分割器、实体抽取器和归纳器。实际用户问题只在查询阶段输入；题型只在评测汇总阶段使用。训练、调参和检索组件不得借用 scorer 的 gold 访问权。

对数据和代码固定 revision、SHA256、解析规则、分词器、抽取器/模型版本、提示词、随机种子和参数。标注生成应写出可审计记录，说明每条派生记录由哪些原始 span 支持。

我们已看过 LoCoMo / LongMemEval 的总体和分类结果。继续在其上调参属于迭代实验。事后按 conversation 划分开发/验证可减少进一步信息混用，但不能重新命名为完全未见测试。最终泛化主张需要新独立数据或在冻结方案后取得的独立评估。

## 3. 比较组

| 组 | 新增能力 | 要回答的问题 |
|---|---|---|
| A0 | 冻结现有 BM25，统一证据内容 | 原始文本可达到什么水平？ |
| A1 | 来源、speaker、session 日期等确定性元数据 | 仅结构化元数据是否有帮助？ |
| A2 | session/事件成员路径 | 上下文分组是否改善分散证据覆盖？ |
| A3 | 实体、角色、时间字段与查询 | 身份和时间组织是否提供额外增益？ |
| A4 | 有界的类型关系扩展 | 关系本身是否优于单纯增加候选？ |
| A5 | claim/模态/版本/冲突 | 历史状态、更新和归属是否更准确？ |
| A6 | 按任务预算做证据覆盖选择 | 同等上下文成本能否找齐更多证据？ |

除累加组外，增加必要的单模块消融。关系扩展可加入同样候选数/扇出但打乱关系的对照，判断增益是否只是检索了更多材料。

若用了 LLM 生成摘要、实体或 claim，必须将抽取模型与推理预算纳入对照。不能把“新结构+更强模型+更多输入 token”的总增益全部归功于结构。向量模型、reranker、查询改写和额外查询次数同理。

## 4. 固定实际证据预算

保留一组 `top-20 原始证据单元` 的比较，并另设固定实际交付 token 数的比较。tokenizer 必须固定，报告完整分布。

**只计真正返回给调用者的叶子证据文本。** 一个 event 节点关联 200 条 turn，不等于返回这个节点就召回了 200 条证据。来源 ID 清单、摘要血缘或未展开的引用不能自动充当已交付证据。

摘要可单独评估“答案支持/压缩质量”，但不能不经逐句证据核验，把所有祖先源文档计入原始证据 recall。原始证据、派生摘要和模型最终答案应各有指标。

## 5. 检索质量指标

- Recall@5/@10/@20：每题 gold 证据覆盖比例，再对题目平均。
- AnyHit@20：至少召回一条 gold 的题目比例。
- AllHit@20：全部所需 gold 都实际交付的题目比例。
- MRR@20：第一条 gold 的倒数排名；它不能替代多跳完整性。
- 固定 token 预算下的 AllHit 和证据密度。
- 按任务类型、证据数量、跨 session 数和时间跨度分组。
- 无回答/无法支持问题单独评估，不混入有答案 recall 分母。

若评估回答生成，需要固定回答模型、提示、上下文长度、随机性和判分协议，并明确它是新增评测。检索指标不能改名为官方 QA 准确率。

## 6. 结构正确性

公开证据检索数据不自动提供所有实体、事件、时间和 claim 的 gold。这些性质需要另行标注协议和经过复核的抽样集，不能因为外键通过就说语义正确。

| 风险 | 需要记录的指标 |
|---|---|
| 同名对象串记忆 | 实体错误合并率、错误拆分率、按 scope 统计 |
| 对话者与事实主体错位 | speaker/subject/actor 归属准确率 |
| 计划变成已发生 | intention→actual 错误率、完成证据缺失率 |
| 时间漂移 | 相对时间解析、有效区间和记录时间问答正确率 |
| 摘要失真 | 否定/条件丢失率、无来源陈述率 |
| 关联幻觉 | 跨事件错误连接率、无证据因果边比例 |
| 错误来源强化 | 同源复制被当作独立印证的比例 |
| 权限传播错误 | 不同读取路径的越权结果数，目标为零 |
| 删除不完整 | 来源删除后仍可从派生视图取回内容的案例数 |

给出分母与置信区间，不只展示“零错误”。较小抽样中没有观察到错误不等于已证明错误率为零。

## 7. 工程成本与性能

质量测量和负载测量分开运行。一次完整查询覆盖用于质量；稳定负载下的多次重复用于延迟和吞吐。不得把有放回的压测样本当作全量质量评测。

测量范围至少包括：索引构建时间、增量写入可见性、派生任务延迟、存储与内存、冷/热查询 p50/p95/p99、有效吞吐 goodput、失败与超时、返回文本/token、以及图扩展候选数。

如果声明“在 200ms 内正确”，分母必须是所有请求，而不只是成功请求。可定义 goodput 为单位时间内同时满足完整证据与端到端时限的请求数。负载生成器是否饱和、数据库是否共享宿主 CPU、连接数、缓存、索引范围必须注明。

本次 SQLite 导入耗时即使被记录，也只描述单次导入验证，不能作为新版本吞吐 benchmark；没有标准负载、重复和稳定性分析时不报“快了几倍”。

## 8. 统计与通过条件

配对比较在相同题目上进行，并按 conversation/scope 聚类分析，避免把同一会话内相关问题当作完全独立样本。LoCoMo 只有少量会话，区间会较宽，应同时提供逐会话结果和逐题差异。

首先冻结预注册的目标：例如多跳 AllHit 的方向、可接受延迟/存储成本、错误身份关联和模态错误上限。具体阈值属于业务要求，不从脑科学论文推导，也不在看完结果后反向设定。

最低验收顺序：

1. 来源隔离和无 gold 泄漏成立。
2. 数据约束及删除/版本行为可重复验证。
3. 同等证据预算下的质量有实际、可解释增益。
4. 质量收益没有被结构错误或过高成本抵消。
5. 在独立数据上验证泛化，再讨论生产迁移。
